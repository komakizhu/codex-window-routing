## 显示器

CoreGraphics/Hammerspoon 报告两块启用的逻辑屏幕。这里记录硬件名称和 UUID，不把 macOS 的“主显示器”当成你的“主屏”。

| macOS 信息 | 名称 | UUID | 坐标与尺寸 |
|---|---|---|---|
| macOS 标记为主显示器 | U27N3G6R4B | `E761F686-7E3C-41E5-BBEB-3BB07918B7E6` | `(0, 0)`，`1920×1080` |
| 另一块显示器 | Sidecar Display (AirPlay) | `532D7571-4385-4C76-AE82-83D54579002B` | `(406, 1080)`，`1366×1024` |

你的屏幕称呼按焦点动态判断：当前正在使用的窗口在哪块屏，那块才是“主屏”；另一块就是“副屏”。鼠标位置和 macOS 的主显示器标记都不参与判断。当前代码只在正好检测到两块屏幕、且能读到焦点窗口时移动；否则停手。UUID 只用来辨认屏幕，不固定指定哪块是副屏。

## Computer Use 关联线索

本轮 CUA 清单显示 Chrome 扩展连到已运行的 Chrome（PID `77629`，bundle ID `com.google.Chrome`），并使用 `Beishi` 配置及已有标签页。Codex 桌面进程本身是 ChatGPT（PID `2454`，bundle ID `com.openai.codex`）。这证明当前浏览器连接使用的是现有 Chrome 会话；不能把 Chrome 所有窗口当成 Codex 专用。

Computer Use 启动了本项目的隔离测试应用并成功移动它的 3 个窗口。真实 Codex 工作窗口、共享 Chrome 窗口和 PiP 之间的关系仍未建立。

## Hammerspoon 首次启动观察

2026-10-30 16:36（Asia/Shanghai）启动时，日志显示当前前台是 System Settings；约 10 秒后 Hammerspoon 激活，随后 ChatGPT 和 Obsidian 先后成为前台应用。Hammerspoon Preferences 窗口也出现过。由于不能证明每次前台切换的来源，我停止了 Hammerspoon，避免观察器持续运行。

初次日志包含 30 条窗口事件和 11 条应用事件。窗口过滤器第一次订阅时把一些已有窗口也报告为 `windowCreated`，所以该批日志不能用来判断 Codex 新窗口的创建顺序。更新后的观察器会在订阅前记录基线，把已有窗口单独标记。

原始本机日志：[`computer-use-observer.jsonl`](/Users/example/.hammerspoon/computer-use-observer.jsonl)。其中保留窗口标题和 AX 描述，可能包含个人内容，不应公开分享。

## 实测结论

隔离测试应用 `org.codex.isolation.WindowProbe` 的 6 个不同窗口都按目标屏 UUID 成功移到 Sidecar。Safari、Chrome、Obsidian 的 5 个现存窗口在相隔 222 秒的两份快照中 ID 和位置完全相同。移动回调内前台应用和鼠标位置没有变化。

这不能证明真实 Codex 工作窗口、共享 Chrome 或 PiP 可被安全识别，也没有验证键盘或鼠标输入隔离。完整结果见[验收报告](test/验收报告.md)。
