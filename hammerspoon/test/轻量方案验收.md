## 修复的实际问题

- 停止旧 Dock/菜单推测路由。新入口只处理当次明确登记的新窗口，程序自行激活不会被当成用户换屏。
- Chrome 改用浏览器直接返回的窗口和标签编号登记。用户继续输入时，不再因无法猜出 macOS 窗口编号而误判；不移动旧个人窗口，不恢复它们的 main 状态。
- Finder 仅在 `make ... with properties` 中提供属性，在实机上仍可能打开“电脑”页面、忽略位置。最终代码明确设置新窗口的 target 与 bounds，并核对目录的文件标识。位置正确不等于目录正确。
- Finder 最初系统权限未生效而超时。用户在本轮确认开启后，实际 AppleEvents 状态为允许，读取版本及新窗口接口恢复；没有换用其他进程绕过权限。
- Obsidian 当前安装器独立配置仍碰共享 CLI socket。额外限制测试主进程写该 socket 和个人配置。第一版外层限制导致本轮测试 helper 启动失败；调整为精确 helper 使用其原有沙箱初始化后恢复启动，没有传 `--no-sandbox` 等关闭参数。正常 Obsidian 主进程 50345、renderer 50349 在本轮前后仍运行，未重启它们。

## 主屏测试窗的错误与纠正

本轮曾错误地把 Agent 主动安排的“独立开窗与输入测试”当成个人查看，在主屏创建窗口。**这是失败，不是验收通过。** 用户指出后已关闭该窗口，停止人工测试按钮并移除其源代码；后续真实测试均使用 automation 副屏。

增加回归检查：没有用户明确主屏查看要求时，`review` / `user` 被拒绝。测试、输入探针、预览或“打算给用户看”不构成该授权。主屏入口额外需要 `userRequestedMain=true`，Agent 不得自行伪造这项许可。用户本人明确在本轮拒绝手测后，没有再让用户完成按钮测试。

## 输入与保护检查的限度

Chrome 三轮中前台应用/窗口未变化，但该轮未取得可比较的 AX 输入对象，因此不能宣称已经逐字符验证了持续打字、或者所有键鼠冲突都不存在。原始审计里的 inputChangedSamples 在起始对象不可读时没有判断意义，报告没有把它当作真实失焦；审计脚本已将缺失对象记为未观察到。

最终 Finder 三轮记录中输入对象可比较，前后相同，前台变化为零。Obsidian 则记录到准确测试 PID 的自行激活，且没有新的物理点击或按键；因此其抢输入失败是明确的。

开始时对个人库进行元数据记录。观察期间有 1 篇既有笔记及 `.obsidian/workspace.json` 的元数据变化；插件目录文件元数据没有变化，既有笔记没有缺失。本轮工厂和脚本没有向这些个人路径写入，也没有擅自还原这些变化，以免覆盖用户或其他任务的工作。该元数据对比不是所有内容的逐字证明。

全部本轮 Chrome 测试标签、Finder 测试窗、Obsidian 测试实例和错误的输入测试窗均已关闭；本机 HTTP 测试服务及临时焦点审计已停止。两个早期 Finder 测试窗经准确编号和默认电脑目标核对后清理，未关闭其他 Finder 窗口。
